| id | package | installed version | lowest fixed version | evidence |
|---|---|---|---|---|
| CVE-2026-50010 | io.netty:netty-handler | 4.1.128.Final | 4.1.135.Final | Reachable and reproduced: when cql.tls.crl.enabled=true (application/src/main/resources/security.yml:56, documented in docs/SETUP.md:184) application/src/main/java/com/ericsson/bss/cassandra/ecchronos/application/ReloadingCertificateHandler.java:357-361 passes the plain-X509TrustManager CustomX509TrustManager (application/src/main/java/com/ericsson/bss/cassandra/ecchronos/application/CustomX509TrustManager.java:29) to SslContextBuilder.trustManager(), and with netty-handler 4.1.128.Final this silently disables the hostname verification requested by cql.tls.require_endpoint_verification=true (application/src/main/java/com/ericsson/bss/cassandra/ecchronos/application/ReloadingCertificateHandler.java:318); a test harness using the shipped jars and the real CustomX509TrustManager completed a TLS handshake to 'localhost' with a certificate issued to 'wrong.example', while the crl.enabled=false path (application/src/main/java/com/ericsson/bss/cassandra/ecchronos/application/ReloadingCertificateHandler.java:370) rejected it, and the same harness with Netty 4.1.135.Final rejected it in both paths |

Reproduction (outside the repository, using the jars from the built distribution): a TLS server presented a certificate issued to `wrong.example`; a Netty client built like `ReloadingCertificateHandler` connected to `localhost` with `endpointIdentificationAlgorithm("HTTPS")`.

| trust manager passed to `SslContextBuilder.trustManager()` | netty-handler 4.1.128.Final (shipped) | netty-handler 4.1.135.Final |
|---|---|---|
| `TrustManagerFactory` (path for `cql.tls.crl.enabled=false`, `ReloadingCertificateHandler.java:370`) | handshake rejected (no matching subject alternative name) | handshake rejected |
| ecChronos `CustomX509TrustManager` (path for `cql.tls.crl.enabled=true`, `ReloadingCertificateHandler.java:357-361`) | **handshake succeeded, hostname mismatch not detected** | handshake rejected |

Scope of the finding: defaults are `cql.tls.enabled=false`, `require_endpoint_verification=false`, `crl.enabled=false` (`application/src/main/resources/security.yml:34, :56`), so only installations that enable CQL TLS with both endpoint verification and CRL checking are affected. In that configuration any certificate that chains to the configured trust store is accepted for any Cassandra host. Not verified: the JMX TLS path and the behaviour with `crl.strict=true` and a populated CRL file (the hostname check is skipped before the CRL logic runs, so the result is expected to be the same).

## 3. Method

1. **Load and count.** All 1089 data rows were read; counts are in section 1.
2. **Deduplicate.** Dependency rows were merged on (advisory, package). GHSA identifiers were mapped to their CVE through the alias lists in OSV and NVD; three Grype rows that carried only a GHSA id were mapped this way (GHSA-rqfh-9r24-8c9r = CVE-2026-24400, GHSA-wg6q-6289-32hp = CVE-2026-5588, GHSA-hjcp-jmpx-g3qm = CVE-2026-64607). Rows for the same advisory from different tools, from the agent distribution and from the different `pom.xml` files of the source tree are one issue; every source tool is kept. The same CVE on two different artifacts (thymeleaf and thymeleaf-spring6, tomcat-embed-core and tomcat-embed-websocket) is kept as two issues because the fix targets differ. PMD rows were merged per rule. Only one merged issue had conflicting scanner severities (CVE-2025-66614: critical in one row, medium in ten); the highest is used as the scanner severity.
3. **Verify dependency presence.** The project was built with `mvn -B install -Pbuild-cassandra-test-jar -DskipTests=true`; `mvn dependency:tree` was resolved for all modules and the built distribution `ecchronos-binary-6.1.4.tar.gz` was unpacked. For every dependency issue the installed version reported by the scanners matches the resolved tree. All flagged packages ship in the distribution `lib/` directory except assertj-core, bcpkix-jdk18on and httpclient5, which are test scope only.
4. **NVD.** Every CVE in the export (89 distinct ids, including the medium and low ones) was fetched from the NVD API at one request per 6.5 seconds or slower. All 89 were found. The CVSS scores in the evidence column are the scores in the NVD record (source NVD or CNA/ADP as marked).
5. **Verify feature use.** For each issue the precondition named in the NVD/GHSA text was checked against the main sources, the shipped configuration files and the distribution. File and line references are relative to the repository root. Three items were additionally tested with the shipped jars: CVE-2026-50010 (section 2), the Thymeleaf expression-injection CVEs (the shipped `error.html` rendered with injection payloads as model values) and CVE-2026-89407 (an 80,000-digit string bound to the REST request type and to a control type).
6. **Verify code findings.** All 131 PMD locations were opened in the source tree; the result per rule is in the evidence column.
7. **Bucket.** critical = exploitable through ecChronos's own code or documented configuration with security impact; high = vulnerable code reachable with default or common configuration; medium = vulnerable code on a reachable path but exploitation depends on conditions that could not be verified; low = vulnerable feature not used or not enabled, test scope only, or no security impact. Effort: S = version property change or small local edit, M = coordinated change (dependency override not managed by an existing property, or many locations), L = no consumable fix on the current release line.

## 4. Limitations and items that could not be verified

- CVE-2026-24880 (Tomcat chunk-extension request smuggling) and CVE-2026-41853 (Spring multipart request smuggling) need a front proxy that parses requests differently from Tomcat/Spring. ecChronos ships no proxy and binds the REST server to `localhost:8080` by default (`application/src/main/resources/ecc.yml:342-343`); deployment topologies were not available, so both are kept at medium.
- CVE-2026-47884 and CVE-2026-47890 (spring-webmvc): NVD lists the 6.2 line as fixed in 6.2.20, which was not available on Maven Central through the configured mirror at the time of triage (latest published 6.2.x: 6.2.19). The scanners list only 7.0.9. Both are relabelled to low because the features are not used; they will keep appearing in scans until a 6.2.20 release can be consumed.
- Tomcat issues fixed in 10.1.58: this version is not published on Maven Central (10.1.57 and 10.1.59 are); the first consumable fixed version is 10.1.59.
- Jackson: no fixed 2.20.x release is published on Maven Central; the fix path is the 2.21 line (2.21.7 covers every Jackson finding in the export).
- "Not used" statements are based on searches of the main sources (`application`, `core`, `rest`, `connection`, `connection.impl`, `fm`, `fm.impl`), the shipped configuration and the jars in the distribution. Third-party internals (for example how the Cassandra driver assembles its Netty pipeline) were not audited beyond these searches. Operator overrides of Spring properties at deployment time are outside what the repository shows.
- Fix versions were checked for availability on Maven Central but not built or tested against ecChronos.
